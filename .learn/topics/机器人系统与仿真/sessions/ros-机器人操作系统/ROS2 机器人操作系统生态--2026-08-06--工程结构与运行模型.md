## Positioning

前两次会话回答了「ROS2 是什么」和「它与 ROS1 有何不同」，这次会话向下走一层，回答「一个真实的 ROS2 工程在磁盘上长什么样、如何被构建、如何被启动、节点内部又是怎样被调度执行的」喵。

这一层是把「会写单个节点」升级为「会组织整个机器人软件工程」的关键台阶，也是 launch、Nav2、MoveIt 等后续内容共同依赖的地基喵。

## Analogy

可以把一个 ROS2 工程想象成一座乐高工厂喵。

**package（功能包）** 是标准化的乐高零件盒：每盒有清单（`package.xml`）写明自己叫什么、依赖哪些其他盒子，盒内零件（节点代码、消息定义、配置文件）按固定格子摆放喵。

**workspace（工作区）** 是装配车间：所有零件盒集中放在车间的 `src` 货架上，流水线加工后成品摆进 `install` 成品区喵。

**colcon** 是流水线本身：它读取每盒的清单，按依赖顺序逐盒加工，谁依赖谁就后加工谁喵。

**source 环境脚本** 相当于给车间通电：不通电时，成品区里摆得再整齐,`ros2 run` 也找不到任何东西喵。

**launch 文件** 是总装说明书：一页纸写清「先装底盘、再装传感器、参数用这套、这两个接口要接在一起」，照着执行就能一键把几十个节点拉起来喵。

**生命周期节点** 像带开机自检的精密设备：先配置、再激活，出问题可以停用而不必拆掉重装喵。

**执行器（executor）** 是车间调度员：节点里的回调函数只是待办事项，调度员决定谁先做、能不能几件事同时做喵。

## Core Mechanism

### 1. workspace：四个目录的约定

一个典型工作区就是一个普通目录（习惯叫 `ros2_ws`），核心约定只有一条：源码放 `src`，其余目录由工具生成喵。

```
ros2_ws/
├── src/        # 你唯一手动维护的目录，放若干 package
├── build/      # colcon 的中间产物，可随时删除重建
├── install/    # 构建成品 + 环境脚本，ros2 run 从这里找程序
└── log/        # 每次构建的日志
```

工作区还支持**叠加（overlay）**：先 source ROS2 发行版自带的 underlay（如 `/opt/ros/humble/setup.bash`，Windows 上是 `install\setup.ps1` 形式），再 source 自己工作区的 overlay，同名包时 overlay 覆盖 underlay，这让你可以只改一个包而不动系统安装喵。

### 2. package：ROS2 世界的最小发布单元

package 是构建、依赖和分发的原子单位，一个包做一类事（驱动、算法、消息定义、launch 集合）喵。

Python 包（`ament_python` 构建类型）的最小结构如下喵：

```
patrol_robot/
├── package.xml          # 身份证：名称、版本、依赖声明
├── setup.py             # 安装脚本：把哪些脚本注册成可执行入口
├── resource/patrol_robot
└── patrol_robot/        # 与包同名的 Python 模块目录
    ├── __init__.py
    └── patrol_node.py
```

C++ 包用 `ament_cmake` 构建类型，用 `CMakeLists.txt` 替代 `setup.py`，其余思想一致喵。

有一个重要的工程惯例：**自定义消息 / 服务 / 动作定义要放进单独的接口包**（如 `patrol_interfaces`），因为消息生成依赖 `rosidl` 的 CMake 流程，纯 Python 包无法生成消息；而且接口独立成包后，别的团队可以只依赖接口而不依赖你的实现喵。

### 3. colcon：按依赖拓扑排序的构建器

在工作区根目录执行 `colcon build`，它扫描 `src` 下所有 `package.xml`，按依赖关系拓扑排序，逐包调用对应构建系统，产物进 `install` 喵。

Python 开发有一个高频技巧：`colcon build --symlink-install` 让 `install` 里的脚本以符号链接指向源码，改完代码不用重新 build 就能生效（新增文件或改 `setup.py` 时仍需重建）喵。

构建完成后必须 source 对应平台的环境脚本（PowerShell 下是 `. .\install\setup.ps1`，Linux 下是 `source install/setup.bash`），这一步把包的路径注入环境变量，此后 `ros2 run <包名> <可执行名>` 才能找到你的节点喵。

### 4. launch：用 Python 描述系统拓扑

真实机器人系统动辄几十个节点，launch 文件把「启动哪些节点、每个节点用什么参数、话题怎么重映射、什么条件下才启动」写成一份可重复执行的描述喵。

ROS2 的 launch 主推 Python 格式（也支持 XML/YAML）：Python 格式的本质是返回一个 `LaunchDescription` 对象，因此可以用变量、条件和循环生成复杂拓扑，例如根据一个 `use_sim_time` 参数决定接真机驱动还是 Gazebo 喵。

要点是分清两个阶段：launch 文件**描述**要启动什么（生成描述对象），`ros2 launch` 命令才真正**执行**启动；每个节点仍是独立进程，launch 进程只负责拉起和监督它们喵。

### 5. 生命周期节点与组件化：面向产品的两种进阶形态

普通节点一启动就开始工作，但产品级系统需要更受控的启动顺序，例如「先确认地图加载完成，再激活定位，再激活规划器」喵。

**生命周期节点（lifecycle node）** 给节点加了一个标准状态机：`unconfigured → inactive → active`，通过 `configure`、`activate`、`deactivate`、`cleanup` 等受管切换推进，Nav2 的各个服务器就全部是生命周期节点，由一个 lifecycle manager 统一编排喵。

**组件化（composition）** 解决另一个问题：进程太多时，进程间通信的序列化开销可观；把多个节点编译成组件装载进同一个容器进程，同进程内的话题传输可以走零拷贝路径，这是 ROS1 中 nodelet 思想的正式化喵。

### 6. 执行器与回调组：节点内部的调度模型

`rclpy.spin(node)` 背后是一个**执行器**在循环干三件事：等待事件（消息到达、定时器到期、服务请求）、取出对应回调、执行它喵。

默认的单线程执行器一次只执行一个回调，因此任何一个回调阻塞（比如在订阅回调里 `time.sleep(5)` 或跑一次慢推理），整个节点的定时器和其他订阅都会停摆，这是新手最常撞上的「节点卡死」根源喵。

需要并发时，用 `MultiThreadedExecutor` 搭配**回调组**：同一个互斥组（`MutuallyExclusiveCallbackGroup`）内的回调仍然串行以保护共享状态，不同组或可重入组（`ReentrantCallbackGroup`）的回调才允许并行，这套机制让你显式声明「哪些回调可以同时跑」喵。

把六层连起来看：package 组织代码，workspace 汇集 package，colcon 把它们变成可运行成品，launch 把成品组装成系统，生命周期管控系统的启停节奏，执行器决定每个节点内部的回调如何被调度——这就是 ROS2 工程的完整运行模型喵。

## Code Example

下面用一个巡逻机器人的最小工程骨架串起「包定义 → 入口注册 → launch 编排」三个环节，代码为教学示例喵。

先看包身份证 `package.xml` 的核心部分喵：

```xml
<?xml version="1.0"?>
<package format="3">
  <name>patrol_robot</name>
  <version>0.1.0</version>
  <description>巡逻机器人示例包</description>
  <maintainer email="dev@example.com">dev</maintainer>
  <license>Apache-2.0</license>

  <depend>rclpy</depend>
  <depend>std_msgs</depend>
  <depend>geometry_msgs</depend>

  <export>
    <build_type>ament_python</build_type>
  </export>
</package>
```

`<depend>` 声明的依赖会被 colcon 用来排构建顺序，也会被 `rosdep` 用来一键安装系统依赖，所以依赖要如实声明而不是只求能跑喵。

再看 `setup.py` 中最关键的入口注册喵：

```python
# setup.py（节选）
entry_points={
    'console_scripts': [
        'patrol_node = patrol_robot.patrol_node:main',
        'battery_monitor = patrol_robot.battery_monitor:main',
    ],
},
```

`console_scripts` 的每一行把「可执行名 = 模块路径:函数」注册给 ROS2，等号左边的名字就是 `ros2 run patrol_robot patrol_node` 里用到的可执行名喵。

最后是把两个节点一键拉起的 `launch/patrol_launch.py` 喵：

```python
# launch/patrol_launch.py
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node


def generate_launch_description():
    use_sim_time = LaunchConfiguration('use_sim_time')

    return LaunchDescription([
        DeclareLaunchArgument(
            'use_sim_time', default_value='false',
            description='是否使用仿真时钟'),

        Node(
            package='patrol_robot',
            executable='patrol_node',
            name='patrol_node',
            parameters=[{'use_sim_time': use_sim_time,
                         'patrol_speed': 0.3}],
            remappings=[('/cmd_vel', '/base/cmd_vel')],
        ),

        Node(
            package='patrol_robot',
            executable='battery_monitor',
            name='battery_monitor',
            parameters=[{'low_battery_threshold': 0.2}],
        ),
    ])
```

`generate_launch_description` 是 launch 系统约定的入口函数，返回的 `LaunchDescription` 就是「总装说明书」本身喵。

`DeclareLaunchArgument` 声明了一个命令行可覆盖的启动参数，运行 `ros2 launch patrol_robot patrol_launch.py use_sim_time:=true` 即可切到仿真时钟，而不用改任何代码喵。

第一个 `Node` 动作展示了两件工程日常：`parameters` 把配置注入节点（对应节点内的 `declare_parameter`），`remappings` 把节点代码里写的 `/cmd_vel` 在部署时改接到 `/base/cmd_vel`，实现「代码不动、接线可换」喵。

把这套工程跑起来的完整命令序列如下（PowerShell）喵：

```powershell
# 在 ros2_ws 工作区根目录
colcon build --symlink-install
. .\install\setup.ps1
ros2 launch patrol_robot patrol_launch.py use_sim_time:=false
```

三步分别对应：流水线加工、给车间通电、按说明书总装，顺序缺一不可喵。

## Common Misconceptions

第一个误区是构建后忘记 source `install` 下的环境脚本，或在旧终端里运行，导致 `ros2 run` 报「package not found」；每开一个新终端都要重新 source，这不是构建失败而是环境未注入喵。

第二个误区是改了 Python 代码却发现行为没变，原因是没用 `--symlink-install` 构建，`install` 里仍是旧代码的拷贝；要么加该选项重建一次，要么每次改动后重新 `colcon build` 喵。

第三个误区是把自定义 msg/srv 定义直接塞进 `ament_python` 包，结果消息死活生成不出来；消息生成走 `rosidl` 的 CMake 流程，必须放在 `ament_cmake` 类型的独立接口包里喵。

第四个误区是以为 launch 把所有节点合并成了一个进程；launch 只是统一拉起和监督，各节点仍是独立进程，真正把多个节点放进同一进程的是组件化 composition 喵。

第五个误区是在订阅回调里做耗时操作（睡眠、大模型推理、阻塞 IO）后奇怪「定时器怎么不走了」；默认单线程执行器一次只跑一个回调，耗时操作要么拆到别的节点，要么用多线程执行器加回调组显式放行并发喵。

第六个误区是把 `build/` 和 `install/` 提交进 git 或手工修改其中文件；这两个目录是纯生成物，出现诡异构建问题时的标准动作反而是删掉它们重新构建喵。

## Socratic Check

问题 1：如果把巡逻逻辑和电池监控写成同一个节点里的两个定时器，与拆成两个节点相比，在部署和故障隔离上各损失了什么喵？

答案：同一节点意味着同一进程，电池监控代码崩溃会连带巡逻逻辑一起挂掉，也无法单独重启或把两者分到不同机器上；而拆成两个节点后各自独立启停、独立崩溃，只是多了一点进程间通信开销，若既想要隔离的代码结构又想省通信开销，组件化 composition 正是折中方案喵。

问题 2：Nav2 为什么要用生命周期节点加 lifecycle manager，而不是让各服务器一启动就各自开始工作喵？

答案：导航栈内部有严格的就绪顺序——地图没加载完就激活定位、定位没收敛就激活规划器都会产生错误行为；生命周期节点把「进程已启动」和「功能已激活」分离成两个状态，lifecycle manager 按依赖顺序逐个 configure 再 activate，从而把启动顺序从「碰运气」变成「可编排」喵。

## Quick Summary

- ROS2 工程的静态结构是三层：package 是最小构建与分发单元，workspace 汇集若干 package，colcon 按依赖拓扑构建并要求 source 环境脚本后才可运行喵。
- launch 文件用 Python 描述「启动哪些节点、什么参数、怎样重映射」，把几十个进程的系统固化成一条可重复的启动命令喵。
- 生命周期节点提供 configure/activate 受管状态机解决启动顺序问题，组件化把多节点装进同一进程换取零拷贝通信喵。
- 节点内部由执行器调度回调，默认单线程执行器下任何阻塞回调都会卡住整个节点，并发需求要用多线程执行器加回调组显式表达喵。
