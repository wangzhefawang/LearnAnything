## Positioning

前几次会话讲的是 ROS2 的概念模型和工程结构，这次是**实地巡览**：通过 `robot254-connect` 接入包 SSH 进一台正在运行的真实机器人 `autolife-sim-robot-254`（Ubuntu 24.04 + ROS 2 Jazzy 共享仿真机），全程只读地观察一个活着的 ROS2 生态——78 个话题、14 个节点、已连续运行 16 天的完整机器人软件栈喵。

教科书告诉你 ROS2「应该」长什么样，这台机器告诉你它「实际」长什么样，两者的差异正是工程经验所在喵。

## Analogy

如果说之前的学习像读解剖学教科书，这次就是跟着医生查房喵。

`ros2 topic list`、`ros2 node info`、`ros2 topic hz` 这些 CLI 工具就是听诊器和化验单：不打开任何代码、不打扰病人（不改任何状态），仅凭「听」和「量」就能诊断出这台机器人的子系统划分、数据流健康度、甚至哪个器官正处于休眠状态喵。

而我们发现的「激光雷达话题存在却没有数据」就像化验单上的一个异常指标：器官（话题端点）在，血流（消息流）却是零，顺藤摸瓜找到病因是对应的服务被人为停掉了喵。

## Core Mechanism

### 1. 巡览用的只读工具箱

这次巡览只用了这些命令，它们合起来就是 ROS2 生态的「体检工具箱」喵：

- `ros2 topic list` / `ros2 node list` —— 看图结构（有哪些端点和参与者）喵
- `ros2 topic type <topic>` —— 看接口契约（每条数据流的消息类型）喵
- `ros2 node info <node>` —— 解剖单个节点（它订阅什么、发布什么、提供什么服务）喵
- `ros2 topic hz` / `ros2 topic echo --once` —— 量数据流的脉搏（频率、抖动、内容）喵
- `systemctl --user list-units` —— 看 ROS 之外的进程托管层喵
- `curl http://127.0.0.1:8091/api/state` —— 看与 ROS 并存的 HTTP 服务喵

所有命令都经 `Invoke-Robot254.ps1 -Ros` 执行，它自动补上非交互 SSH 缺失的 ROS 环境（source `/opt/ros/jazzy/setup.bash` + 注入 DDS 变量），这个坑之前的会话讲过喵。

### 2. 全景数字：78 个话题、14 个节点意味着什么

实测这台机器有 **78 个话题、仅 14 个节点**，平均每个节点挂着五六条话题，多的（如机械臂控制节点）一个就占 19 条喵。

这修正了教程给人的直觉——教程里一个节点发一个话题，真实系统里**节点是按职责划分的粗粒度单元，话题是按数据流划分的细粒度接口**，一个「机械臂控制」职责天然对应几十条命令入口和状态出口喵。

机器已连续运行 16 天（uptime 16 days），22 核上负载稳定在 6.3，Isaac Sim 仿真循环已执行 402 万步——这是「机器人软件是长期运行的服务而非跑完就退的脚本」的直观证据喵。

### 3. 解剖一个真实节点：机械臂控制器

`ros2 node info /node_robot_arm_control_0_254` 的实测结果很有代表性喵：

- **8 个订阅**全是命令入口：目标关节位置、目标速度、夹爪力矩、清错、使能开关等喵。
- **11 个发布**全是状态出口：全身关节状态、灵巧手状态、左右手六维力、触觉阵列等喵。
- **7 个服务**全是 `rcl_interfaces` 的参数服务——不是业务代码写的，是每个 ROS2 节点自动生成的参数基础设施喵。
- **Action Servers: 无**——整台机器没有用一个原生 Action，这是下一节的伏笔喵。

「订阅=输入命令、发布=输出状态」这个模式就是控制类节点的标准形状，看懂一个就能看懂一类喵。

### 4. 消息类型的双轨制：标准消息 vs String+JSON

实测话题类型呈现清晰的两条轨道喵：

| 轨道 | 实例 | 类型 |
| --- | --- | --- |
| 标准消息 | `/topic_gv_imu_0_254` | `sensor_msgs/msg/Imu` 喵 |
| 标准消息 | `/topic_gv_wheel_odom_0_254` | `nav_msgs/msg/Odometry` 喵 |
| 标准消息 | `/map`、`/tf`、`/amcl_pose` | `OccupancyGrid`、`TFMessage`、`PoseWithCovarianceStamped` 喵 |
| String 轨道 | `/robot_navigation_0_254/go` | `std_msgs/msg/String` 喵 |
| String 轨道 | 机械臂全部 19 条业务话题 | `std_msgs/msg/String` 喵 |

规律是：**凡是要接入现成生态（RViz 可视化、AMCL、地图、TF 树）的数据用标准消息，凡是自家业务命令一律用 String 装 JSON** 喵。

String+JSON 的收益是不用维护接口包、字段随便加、跨语言与 Web 桥接零成本（Dashboard 的 FastAPI 直接转发 JSON 到 WebSocket）；代价是失去编译期类型检查、`ros2 topic echo` 看到的是一坨字符串、标准工具无法直接可视化喵。

这正是上次「自定义消息要单独建 `ament_cmake` 接口包」那条规则的现实回声——这家公司选择了绕开接口包的工程路线，两种选法都存在于产业界喵。

### 5. 用 Topic 手工实现 Action 语义：导航模块的启示

教科书说「导航去目标点应该用 Action」，但这台机器的导航接口是四个 String 话题喵：

```
/robot_navigation_0_254/go                     # ≈ Action 的 goal
/robot_navigation_0_254/cancel                 # ≈ Action 的 cancel
/robot_navigation_0_254/navigating_feedback    # ≈ Action 的 feedback
/robot_navigation_0_254/is_navigating          # ≈ Action 的 status
```

对照 Action 的四要素（goal / cancel / feedback / result-status），会发现他们用 Topic 逐一手工复刻了 Action 的语义喵。

为什么不用原生 Action？可能的工程理由：String 话题对 Web/Dashboard 桥接最友好、不用生成 Action 接口代码、调试时 `ros2 topic pub` 一条命令就能触发导航；付出的代价是没有 goal ID 管理（无法区分并发目标）、没有类型安全、取消与结果的时序要自己保证喵。

这是「机制 vs 语义」的一课：Action 是 ROS2 提供的**机制**，但它承载的**语义**（可取消的长任务）也可以用别的机制实现，成熟工程师看的是语义是否完整，而不是是否用了教科书钦点的机制喵。

### 6. 话题存在 ≠ 有数据：一次现场诊断

实测 `/topic_gv_front_lidar_0_254` 在 `topic list` 里存在，但 `ros2 topic hz` 观测 5 秒收不到一条消息喵。

原因用 `systemctl --user` 立刻查明：`gv-control-service`（底盘控制服务）处于 `inactive dead`，而这台共享机上带 `Restart=always` 的单元变 dead 通常意味着有同事主动 stop 了它喵。

这揭示了 DDS 图的一个重要性质：**话题是端点声明，不是数据保证**——只要曾有节点声明过订阅或发布，话题名就留在图里，数据流断了话题名也不消失喵。

排查「话题有名无数据」的标准链条就是这次走的路：`topic hz` 确认无流量 → `topic info` 看发布者数量 → `systemctl` / 进程层找发布者的下落喵。

对照组：`/topic_gv_wheel_odom_0_254` 实测 **62.5 Hz、抖动仅 0.2 ms**，说明轮式里程计回路活得非常健康，也顺带说明 62.5 Hz 这个频率是发布节点自己的定时器决定的——ROS2 只负责传输，不负责保证任何发布频率喵。

### 7. ROS 图之外的共生系统

`systemctl --user` 的完整清单展示了 ROS 生态的「宿主环境」喵：

- **机器人业务服务**：arm-control、vision、gv-slam、dashboard-backend 等 active running，gv-control 人为 dead 喵。
- **普通 Linux 桌面服务**：GNOME 会话、D-Bus、文件管理器守护进程和机器人服务并排跑——真实机器人本质上就是一台 Ubuntu 电脑喵。
- **Isaac Sim**：不归 systemd 管、手动拉起，通过 `127.0.0.1:8091` 的 HTTP API 暴露状态（实测 `ready: true`，加载的是 `robot_v2_2.usd` 模型，对应同一份 URDF）喵。
- **Dashboard**：FastAPI 的 `/health` 实测返回 `ros_ready: true` 与四个组件状态，其中 `ros_wrapper` 就是把 ROS 话题桥接成 WebSocket 的组件喵。

所以一台产品级机器人的完整生态是四层共生：**DDS 上的 ROS 图（通信）+ systemd（进程保活）+ 仿真引擎（物理）+ HTTP/WebSocket 桥（人机界面）**，ROS2 只是其中的通信层，这与之前会话的论断在实机上完全对上了喵。

顺带一个实证细节：每条 ROS 命令启动时打印的两行警告（`NetworkInterfaceAddress deprecated`、`lo is not multicast-capable: disabling multicast`）正是「CycloneDDS 绑定回环网卡、ROS 流量不出机器人」的现场证据，这解释了为什么开发机上永远 `ros2 topic list` 为空、必须 SSH 上机操作喵。

## Code Example

本次巡览的完整只读命令序列如下，可以作为今后「接手任何一台陌生 ROS2 机器人」的标准体检流程喵。

```powershell
# 经 robot254-connect 的封装脚本远程执行（自动补 ROS 环境）
$r = "D:\SAVE\robot254-connect\Invoke-Robot254.ps1"

# 1. 宿主体检：机器身份、运行时长、负载
& $r "hostname && uptime && uname -r && nproc"

# 2. 图结构：话题与节点全景
& $r -Ros "ros2 topic list"      # 实测 78 条
& $r -Ros "ros2 node list"       # 实测 14 个

# 3. 解剖重点节点：输入输出接口一目了然
& $r -Ros "ros2 node info /node_robot_arm_control_0_254"

# 4. 数据流脉搏：频率与抖动
& $r -Ros "timeout 6 ros2 topic hz /topic_gv_wheel_odom_0_254"
# 实测 average rate: 62.500  std dev: 0.00025s —— 健康

# 5. 进程托管层：ROS 之外看 systemd
& $r -Systemd "systemctl --user list-units --type=service --all --no-pager"
# 实测 gv-control-service = inactive dead —— 雷达话题无数据的病因

# 6. 共生的 HTTP 服务
& $r "curl -s -m 5 http://127.0.0.1:8091/api/state | head -c 400"   # Isaac
& $r "curl -s -m 5 http://127.0.0.1:9001/health"                     # Dashboard
```

多行脚本（带 `$` 变量、for 循环）必须改用 `-Script @'...'@` 单引号 here-string，否则 PowerShell 会在本地就把 `$t` 展开吃掉——这次巡览中一条 for 循环命令就实际踩了这个坑，报 `syntax error: unexpected end of file`，换 here-string 后通过喵：

```powershell
& $r -Ros -Script @'
for t in /robot_navigation_0_254/go /topic_gv_imu_0_254 /map /tf; do
    printf '%s  ' "$t"
    ros2 topic type "$t"
done
'@
# 实测输出：
# /robot_navigation_0_254/go  std_msgs/msg/String
# /topic_gv_imu_0_254  sensor_msgs/msg/Imu
# /map  nav_msgs/msg/OccupancyGrid
# /tf  tf2_msgs/msg/TFMessage
```

这段输出就是「双轨制」的直接证据：同一台机器上，IMU、地图、TF 走标准消息，业务命令走 String 喵。

## Common Misconceptions

第一个误区是把「话题在 `topic list` 里」当作「有数据在流」；话题是端点声明而非数据保证，本次实测的激光雷达话题就是有名无流，真实病因在进程层（服务被 stop）而非 ROS 层喵。

第二个误区是以为节点数和话题数是一个量级；实测 14 个节点对 78 条话题，真实系统的节点是粗粒度职责单元，单个控制节点挂十几条话题是常态喵。

第三个误区是以为业务话题都应该定义自定义消息类型；产业界存在成熟的 String+JSON 路线，用类型安全换取迭代速度和 Web 桥接便利，两条路线各有取舍而非对错喵。

第四个误区是以为长任务必须用原生 Action；这台机器用四个 Topic 手工复刻了 Action 的 goal/cancel/feedback/status 语义，机制可以替换，语义完整才是关键喵。

第五个误区是把 `ros2 node info` 里的七个参数服务当成业务接口；它们是每个 ROS2 节点自动生成的 `rcl_interfaces` 参数基础设施，解读节点时应直接跳过喵。

第六个误区是以为消息频率是 ROS 保证的；62.5 Hz 是发布节点自身定时器与系统负载共同决定的，ROS2 的 QoS 只约束传输行为（可靠性、缓存），不产生也不承诺发布频率喵。

## Socratic Check

问题 1：`/robot_navigation_0_254` 的 go / cancel / navigating_feedback / is_navigating 四个话题，分别对应原生 Action 的哪个要素，这种自建方案在什么场景下会露出短板喵？

答案：go 对应 goal、cancel 对应取消请求、navigating_feedback 对应 feedback、is_navigating 对应 status/result；短板在并发场景——原生 Action 有 goal ID 能区分「取消的是哪一次导航」，四话题方案里 cancel 只能全局取消，若两个客户端先后下发目标，反馈和取消就会串台喵。

问题 2：如果明天接手另一台陌生的 ROS2 机器人，你会按什么顺序跑哪几条命令建立全貌喵？

答案：先 `ros2 node list` + `ros2 topic list` 看图结构规模，再对核心控制节点跑 `ros2 node info` 看输入输出形状，然后对关键数据流跑 `ros2 topic hz` 量健康度，接着 `ros2 topic type` 抽查消息类型判断标准/自定义双轨的分界，最后跳出 ROS 用 `systemctl` / `ps` 看进程托管层——正是本次巡览的顺序，全程只读喵。

## 追问与解答

### Q1（2026-08-06）节点名不是文件夹

**问：** ros2 node info /node_robot_arm_control_0_254 不是这文件夹在哪啊，没找到

**答：**

这是个非常典型的误会喵——`/node_robot_arm_control_0_254` **不是文件夹，也不是文件路径**，它是 ROS 图里的**节点名**喵。

**为什么长得像路径**：ROS 故意借用了 Unix 路径的写法来命名运行时资源——节点名、话题名都以 `/` 开头、用 `/` 分层（比如 `/robot_navigation_0_254/go`），这套「名字」只存在于**正在运行的 DDS 通信图里**，是内存中的注册信息，不对应磁盘上的任何目录，所以你在文件系统里永远找不到它喵。

**它的「实体」在哪**：这个名字背后是机器人上一个正在运行的进程喵。三个层面对应关系是：

| 你想找的 | 实际位置 | 查看方式 |
| --- | --- | --- |
| 运行时节点名 | DDS 图（内存里） | `ros2 node list` 喵 |
| 承载它的进程 | systemd 服务 `arm-control-service` | `systemctl --user status arm-control-service` 喵 |
| 源代码 | 机器人上 `~/Documents/` 下的 SDK 仓库 | 那才是真正的文件夹喵 |

节点名是代码在启动时自己声明的——源码里有一行类似 `Node('node_robot_arm_control_0_254')`，进程一跑起来，这个名字就注册进 DDS 图，进程一停名字就消失喵。

**另外要注意执行位置**：这条命令必须**在机器人上**跑，在你自己的开发机上跑（哪怕装了 ROS2）也会报「node not found」，因为这台机器的 DDS 绑在回环网卡，图信息不出机器人喵。正确姿势是通过封装脚本远程执行喵：

```powershell
& "D:\SAVE\robot254-connect\Invoke-Robot254.ps1" -Ros "ros2 node info /node_robot_arm_control_0_254"
```

### Q2（2026-08-06）ros2 命令与当前目录无关

**问：** 在机器人里面的任意文件夹运行这个命令都可以吗

**答：**

可以喵——`ros2` 系列命令**跟你当前在哪个文件夹完全无关**喵。

**原因**：`ros2 node info`、`ros2 topic list` 这类命令不读磁盘上的任何项目文件，它们是向**内存里的 DDS 通信图**发起查询——本质是你的命令行进程临时加入 DDS 网络、问一圈「都有谁在、谁发什么」，所以在 `~`、`/tmp` 还是任何目录下运行，结果一模一样喵。

真正决定命令能不能跑的不是**位置**，而是**环境**喵：

| 条件 | 不满足时的报错 |
| --- | --- |
| source 过 `/opt/ros/jazzy/setup.bash` | `ros2: command not found` 喵 |
| 有正确的 DDS 变量（`ROS_DOMAIN_ID`、`CYCLONEDDS_URI` 等） | 命令能跑但看到的图不对/为空喵 |

这也是 `Invoke-Robot254.ps1 -Ros` 存在的意义——它保证的就是环境，而不是目录喵。

不过要小心，**少数 ROS 相关命令是吃当前目录的**，别混淆喵：

- `colcon build` —— 必须在工作区根目录跑（它找 `src/`）喵
- `source install/setup.bash` —— 相对路径，位置错了 source 到空喵
- `ros2 bag record` —— 录制文件写到**当前目录**，在哪跑就存哪喵
- `ros2 launch <文件路径>` 用相对路径指 launch 文件时也吃目录（用 `<包名> <launch名>` 形式则不吃）喵

一句话总结：**查询图的命令看环境不看目录，操作文件的命令才看目录**喵。
